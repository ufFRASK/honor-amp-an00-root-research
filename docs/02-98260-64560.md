# CVE-2026-98260（及同机理 64560）

## 机理

`execve → de_thread` 与 POSIX CPU timer 的 `cleanup_timerqueue()` 竞争，`k_itimer` 被 `call_rcu` 释放后仍有悬空节点留在 timerqueue/rbtree 里；此后一次 `rb_erase` 在已释放对象上做树操作，形成 8 字节写。

- `posix_timers_cache`：objsize 264 B，**31 obj / 2 pages**（order-1 8 KiB，8 KiB 对齐）。
- 关键对象：`struct k_itimer`（含 `it.real.timer` 的 rb_node）。

## 实测结论

| 项 | 结果 |
|---|---|
| 触发层 | **确定性成立**：`leader-released≈112–137 ms`、`victim-zombie≈1–25 ms`、`c_done=0`、无 `exec completed after de_thread` |
| 回收层 | slab→buddy 可打通（旧四段序多次出现 `pre-reap delta=31`） |
| 六类通用载体 | **零命中**：IPv6 SRH 256/512/1024/2048、anon mmap、AF_UNIX 16 K skb（含"孤立受控 discard 后即时喷洒"） |
| 同 cache 重占 | 拿不到可控 node（无法控制树指针） |
| `cred_jar` 路线 | `slabinfo` 实测 `192 B / 21 obj / 1 page`，order-0 UNMOVABLE——恰在历史载体覆盖盲区；但取用需要 ftrace 分配地址确认，而本机 tracefs **全 EACCES** |

## 判据修正（重要）

早前结论写作"跨 cache 在本机不可行"，**范围过大**。正确表述是：

> **六类通用载体不可行**；`cred_jar` 专用 cache 页复用 + 分配地址确认这条路**未测**，因为本机无法开启 kmem 事件。

这不是"漏洞不可利用"，而是"环境不给观测/门控"。

## 为什么本机走不通

1. 跨 cache 需要把悬空页交还 buddy 再被目标 cache 拿走，本机 order 与迁移类型组合只对六类载体成立（均未命中）；
2. 同 cache 重占无法让 attacker 控制 rb_node 三个指针，写目标不可选；
3. cred_jar 页复用需要知道"k_itimer 与 cred 落在哪一页"，本机唯一可用的手段是 ftrace，已被 SELinux 封死。
